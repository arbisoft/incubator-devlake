# OpenAPI and REST API Standards

Sources: [OpenAPI Specification](https://spec.openapis.org/oas/latest.html), [RFC 9110 HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110), [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457), [Google API Design Guide](https://cloud.google.com/apis/design), [Microsoft REST API Guidelines](https://github.com/microsoft/api-guidelines).

These rules apply to every new or changed HTTP route. They don't depend on the spec tool: they hold whether the spec is a hand-written OpenAPI 3 file, generated from annotations (swaggo `// @Router …` comments → Swagger 2.0), or generated by any other tool.

**Consistency comes first.** When the existing API already uses a convention (casing, pagination params, error body), new routes follow it, even where this file would choose differently. A new route that adds a second convention is a finding (API-R4). Changing the existing convention is a versioning decision (API-V), not a review fix. The same goes for the handler *shape*: when a framework or the project's router defines it, read every rule here through API-H0.

## API-R — Resource design

- **API-R1 Paths name resources, not actions.** Plural nouns for collections, with the ID as a path param: `GET /connections`, `GET /connections/{connectionId}`. Verbs are only for operations that aren't CRUD and are clearly named as actions (`POST /connections/{connectionId}/test`, `POST /pipelines/{id}:cancel` style). They're never used for things a method already expresses (`/getConnections`, `/deleteUser`).
- **API-R2 Nest at most two levels** (`/connections/{id}/scopes/{scopeId}`). Deeper relationships use a top-level resource with a filter.
- **API-R3 Path params are named after the resource** (`{connectionId}`, not `{id}` on one route and `{connId}` on another), and match the handler's param lookup exactly.
- **API-R4 One style throughout the API.** Path casing, query-param casing, trailing slashes and ID formats match the existing routes.

## API-M — Methods

- **API-M1 GET and HEAD are safe.** They never change state, start jobs or write to the DB.
- **API-M2 PUT and DELETE are idempotent.** Repeating the request gives the same result. Deleting something that's already deleted returns 404 or 204, consistently.
- **API-M3 POST** creates a resource under a collection, or runs an action. **PATCH** is a partial update: fields left out are left unchanged. **PUT** replaces the whole resource. A "PATCH" that clears fields left out of the request is a bug.
- **API-M4 Retried creates are safe**, through an idempotency key or a natural unique key, when clients or jobs may retry (see REL-I1).

## API-S — Status codes

- **API-S1 Success:**
  - `200` returns a body.
  - `201 Created` is for creates, with the new resource or a `Location` header.
  - `202 Accepted` is for async work, with a way to poll it.
  - `204 No Content` has no body.
- **API-S2 Client errors:**
  - `400` for malformed or invalid input.
  - `401` when authentication is missing or wrong, `403` when the caller is authenticated but not allowed.
  - `404` when the resource doesn't exist, or when hiding it from an unauthorized caller.
  - `409` for a conflict or duplicate.
  - `412` / `428` for failed preconditions.
  - `413` for a body that's too large.
  - `422` only if the API already uses it for validation.
  - `429` for rate limits.
- **API-S3 Never `500` for client mistakes.** Bad input, a missing resource or a conflict must map to 4xx. The handler or error mapper translates domain errors (`ErrNotFound` → 404, `ErrConflict` → 409, a validation error → 400). If the project's error kinds carry a status (GO-X1, e.g. `errors.NotFound` → 404, `errors.BadInput` → 400), the code must create the error with the right kind. Wrapping a not-found error in `errors.Default` turns it into a 500.
- **API-S4 Never `200` with an error body**, and never a 2xx on failure.
- **API-S5 Every status a route can return is documented** (API-D3).

## API-E — Errors

- **API-E1 One error schema for the whole API.** It has a stable machine-readable code, a human message, and optionally a `details` field for per-field validation errors. Use the API's existing error type if there is one. Otherwise use RFC 9457 `application/problem+json`.
- **API-E2 No internal details leak to clients:** no raw `err.Error()` from the DB or driver, stack traces, SQL, file paths, hostnames or upstream responses. Log those server-side (OBS-L1) and return a safe message.
- **API-E3 Validation errors name the field** and the rule that failed, so the client can fix the request.
- **API-E4 Error mapping lives in one place** (a mapper or middleware), not repeated in each handler. An error type that carries its own HTTP status and is turned into a response by one shared helper (e.g. `core/errors` kinds) counts as that one place. Breaking the rule means a handler that hard-codes a status that doesn't match the error's kind, or that builds its own error body.

## API-B — Request and response bodies

- **API-B1 Validate all input at the boundary**, before calling the service. When the framework hands over a generic body (API-H0), validation happens as it's decoded into the typed request struct, via the project's decode helper with a validator (e.g. `api.Decode(input.Body, &req, vld)`), or through explicit checks right after. Either way, check:
  - required fields are present;
  - types, formats, ranges and enum values are valid;
  - string lengths and collection sizes are within limits;
  - body size is capped (GO-R4).
  The service may assume it gets valid input. It still enforces business rules.
- **API-B2 DTOs, not persistence models.** Request and response types are separate structs from DB/ORM models. A DB model returned straight to clients leaks internal fields (secrets, internal IDs, soft-delete flags) and ties the API to the schema. Map at the handler boundary.
- **API-B3 Secrets are write-only.** Tokens and passwords may be accepted in requests but are never returned in responses (mask or omit them).
- **API-B4 Consistent JSON field casing** (follow the existing API), set with explicit `json:"…"` tags on every exported DTO field.
- **API-B5 Times** are RFC 3339 strings in UTC (`2026-10-14T09:30:00Z`). Durations have their unit in the name (`timeoutSeconds`) or use ISO 8601.
- **API-B6 Optional vs nullable is explicit.** Use pointer fields or `omitempty` deliberately, and document whether a field can be missing, `null`, or both. A zero value must not be silently read as "not provided" on PATCH.
- **API-B7 Unknown fields:** follow the API's existing policy and the decode helper's behavior. For example, mapstructure-based helpers ignore unknown keys by default, and that isn't a finding unless the endpoint must be strict. Where the endpoint is strict, use `DisallowUnknownFields` or the helper's strict mode.
- **API-B8 Money and precise numbers** are never `float64`. Use strings or integer minor units.

## API-P — Collections

- **API-P1 Unbounded lists are paginated.** Use the API's existing scheme (`page` / `pageSize`, or a `cursor` / `nextCursor`), with a default and a maximum page size enforced on the server.
- **API-P2 The response says how to get the rest:** a `count`/`total`, or a `nextCursor`. The order is stable (sort by a unique key as the tie-breaker), so pages don't overlap or skip items.
- **API-P3 Filter and sort params** are named the same way across endpoints. Unknown sort fields return 400, not a silent default.

## API-V — Compatibility and versioning

- **API-V1 Breaking changes need a new version or a deprecation period.** Breaking changes include:
  - removing or renaming a field, param or route;
  - changing a type or format;
  - making an optional input required;
  - tightening validation;
  - changing the meaning of a status code or field;
  - changing the default sort or page size;
  - removing an enum value.
- **API-V2 Additive changes are fine:** new optional request fields, new response fields, new routes, new enum values *if* clients are documented to tolerate unknown ones.
- **API-V3 Deprecations are marked in the spec** (`deprecated: true`, or `@Deprecated` in swaggo) and give the replacement.

## API-D — Spec (OpenAPI / Swagger)

- **API-D1 Every route is in the spec.** A new or changed handler without spec annotations or entries is a finding. For annotation-based specs (swaggo), the comment block sits directly above the handler: `@Summary`, `@Description`, `@Tags`, `@Accept`/`@Produce` where needed, `@Param` for every path, query, header and body param, `@Success`, `@Failure` and `@Router path [method]`.
- **API-D2 Params are complete and correct:** name, location (`path`/`query`/`header`/`body`), type, `required`, and enum, default and format where they apply. Param names match what the handler actually reads.
- **API-D3 Responses are complete:** every status the handler can return (API-S5), each with its schema. The success schema is the actual DTO type returned, not a placeholder. Error responses reference the shared error schema (API-E1).
- **API-D4 The spec matches the code.** The router's path and method, param names, status codes and types must agree with the handler. Check this by reading the route registration and the handler side by side. A spec that disagrees with the code is worse than no spec.
- **API-D5 Schemas are named types.** The *documented* request and response schemas are named structs, never `object`, `map[string]interface{}` or `interface{}`. Shared shapes are defined once and referenced. This is about the spec, not the framework's input type. A handler that receives a generic map (API-H0) is fine when it decodes it straight into a named struct, and the spec's body param names that struct (`@Param body body models.GithubConnection true "json body"`). Findings: the spec documents a map/object or leaves the body out, or the documented struct isn't the one the handler decodes into.
- **API-D6 Examples** for fields whose format isn't obvious (IDs, cron expressions, time windows, enums).
- **API-D7 Security is declared:** protected routes declare their security scheme. Public routes are deliberately public.
- **API-D8 The spec is updated in the same change.** Regenerate it with the repo's generator (e.g. `make swag` / `swag init`) and make sure it builds. If the generated spec is committed, commit the regenerated file. If it's gitignored, the annotations are the spec of record, and API-D1–D7 are checked on them.

## API-A — Security at the API

- **API-A1 Authentication and authorization on every route that isn't public.** Authorization checks the specific resource (can this caller see *this* connection?), not only "is logged in". Missing object-level checks are a security finding (SEC-A1).
- **API-A2 No secrets in URLs or query strings.** They end up in logs, proxies and browser history. Use headers or the body.
- **API-A3 Rate limits or quotas** on expensive or unauthenticated endpoints.
- **API-A4 CORS** is not `*` with credentials. Allowed origins are explicit.

## API-H — Handler shape

- **API-H0 Framework handler shapes.** Many projects don't use bare `net/http` handlers. Find the project's handler type and the adapter that serves it (for example, in this repo: `plugin.ApiResourceHandler`, i.e. `func(*plugin.ApiResourceInput) (*plugin.ApiResourceOutput, errors.Error)`, served by `handlePluginCall` in `server/api/router.go`). Read it once, then apply every API rule through its equivalents:

  | Concern | net/http form | Framework equivalent (example: this repo) |
  |---|---|---|
  | Request context | `r.Context()` | the context the framework exposes: `input.Request.Context()` |
  | Status | `w.WriteHeader(…)` | `output.Status`, or the returned error kind's HTTP code |
  | Error body | the shared mapper writes it | the adapter writes it from the returned error (`shared.ApiOutputError`) |
  | Input | `r.Body`, `r.URL.Query()`, path vars | `input.Body`, `input.Query`, `input.Params` |
  | Route tests | `httptest` | call the handler directly with a constructed input |

  The framework's own generic types (`Body map[string]interface{}`, `Output.Body interface{}`) are never findings in themselves. What matters is what the handler does with them (API-B1, API-D5, SEC-I6).
- **API-H1 Handlers are thin.** They do four things: parse and validate input (API-B1), call an injected service (DI-B3), map the result to a DTO (API-B2), and map errors to a status (API-E4). Business logic, DB queries and outbound calls in a handler violate SRP-3.
- **API-H2 Handlers pass the request context** to every downstream call that accepts one (GO-C3), so client disconnects cancel the work. Get it the framework's way (`r.Context()`, `input.Request.Context()`, …). If nothing downstream accepts a context (e.g. a DAL whose methods take no ctx), there's no finding. A new ctx-aware call made without passing it is a finding.
- **API-H3 Every new or changed route has tests in the project's handler-test style**, with a fake service (DI-T1): `httptest` for `net/http` handlers, or a direct call with a constructed input for framework handlers (e.g. `GetX(&plugin.ApiResourceInput{Params: …, Body: …})`, asserting `output.Status`/`output.Body` and `err.GetType().GetHttpCode()`). Either way, the tests cover the success status and body, a validation failure that names the field, not found, and the error kind/status. A router-level test is only needed when the change touches routing or middleware.
